# L1, sliced: the living tree, prose-warm

Status: IN PROGRESS on branch `living-tree-l1`. Executes milestone L1 of
`2026-08-13-living-tree-plan.md` §6. Evidence: a nine-agent read of the
post-L0 engine (2026-08-14) — six censuses (append path, aliasing, warm
parser, identity, oracles, fallback) and three independent slice
decompositions under a risk-first, an oracle-first and a value-first lens.
Where the three disagreed the order below follows the risk-first argument,
for the reason recorded in §2.

## 1 · What the censuses settled

Four facts decide the shape of everything below, and each was verified
against the working tree rather than inherited from an earlier document.

**Nothing borrows the source bytes.** Every byte the tree keeps is copied
out of the fed buffer before the feed returns: the line into `curline`, the
remainder into the node's content strbuf, inline literals into a chunk that
borrows the *parent's content* rather than the input, marks and concrete
records as integer offsets. Today's code already proved it — the joined
buffer was freed the instant `document_build` returned. So a chain-owned
buffer may grow and move without invalidating any document already built.

**`refine_blocks` is terminal, and it is the only thing that is.** It stamps
the tree, then does `res = parser->root; parser->root = NULL`, and a parser
whose root is NULL ignores every further feed. Nothing else in the parse
path is one-shot. A warm tick therefore may not call it; the fallback still
can, because the fallback builds its own parser.

**`finalize` is the sole writer of end coordinates, and there is no
un-finalize.** It asserts the node is OPEN before clearing the flag, and
`finalize_blocks` closes the whole spine to the root and destroys the held
partial line. A living tree must be closed to be *published* and must be
reopened to keep *growing* — which is the one claim in this milestone whose
failure has no cheap answer.

**Inline literals borrow the block's content buffer.** A unit that has been
refined holds children pointing into `node->content.ptr`; `add_line` grows
that buffer. So a warm tick's first act on the open leaf must be to retire
its inline children (and free its `inline_concrete`, which is a once-only
assignment), and only then feed bytes. This is the one genuine
use-after-free the milestone creates, and it is not at the byte layer.

## 2 · The order, and why

The risk-first lens named the claim that, if false, forces a redesign back
toward the buried fork: *a tick can speculatively close the open spine to
publish a correct projection, and then exactly undo that close so the next
tick continues as if it never happened.* Everything else in L1 — ownership
moving to the chain, ids minted at creation, revisions by touch — is a
refactor whose failure mode is a bug. That claim is provable COLD: with no
living tree, no ownership change, and no edit to `markdown_core_document_append`.
So it goes early, and the enabling refactors follow it rather than precede
it.

## 3 · Hazards the slices must answer

Each was raised by a census with file:line evidence and is not yet closed;
the slice that owns it is named.

- **The tree dies with the receiver** (slice 5). The tree is allocated from a
  per-document arena and the contract lets a caller free a superseded handle
  at any moment — including the ES and Kotlin reclaim paths, which do
  exactly that. The arena moves to the chain in the same motion as the tree.
- **Fallback after mutation** (slice 7). A line that begins as a paragraph
  continuation can turn out to be a setext underline, a table delimiter row
  or a fence close, by which point `add_line` has already written. The
  eligibility decision must be a pure probe over the arriving bytes and the
  open-spine shape, taken before any write.
- **Stale hashes corrupt the next fallback** (slice 7). A warm tick that
  mutates nodes without restamping the touched spine leaves `subtree_hash`
  lying, and the next fallback's pairing sweeps believe it.
- **The half line is not always truncatable** (slice 3/6). A held partial
  line that is a reference definition or a fence info line runs harvests and
  byte drops that a truncate cannot undo. L1 gates the warm path on the
  shape of the HELD line, not only on the containing block.
- ~~**Kotlin's reuse gate inverts**~~ — CLOSED in slice 4.5: the receiver's
  root extent is now read before the append, so the bound describes the
  receiver even once a successor can share its predecessor's root.
- **The local UBSan is blind to the whole zero-length-on-null class.**
  Apple's sanitizer reports neither a zero offset applied to a null pointer
  (slice 1's `buffer + len`) nor a null passed where a library declares its
  parameter non-null (slice 3b's `memcpy(dst, NULL, 0)`); the Linux
  toolchains CI runs report both, and both were caught there after a green
  local four-config run. Naming `pointer-overflow` explicitly does not help
  — measured: Apple clang accepts the flag and still says nothing. Empty
  buffers, empty chunks and empty counts must be reasoned about, not merely
  run: guard the length before the call, once, where the call lives.
- **The 39-entry inventory's coordinates have drifted.** L0 shifted
  `core/blocks.c`; the measured deltas are −8 for the line-processing sites,
  −6 for `finalize_blocks`, +1 for `finalize`/`add_child`. Verify every
  coordinate against the working tree before using it as a journal spec.

## 4 · What L1 does not do

No journal totality (that is L2): every shape outside the prose set falls
back per tick, and the fallback stays exactly as correct as today's append.
No deletion of `diff.c`, the hash apparatus or the stamp (that is L3, and
only once the fallback rate is zero). No intra-unit incremental inline
parsing, ever — the honest ladder keeps its prose-wall entry.
